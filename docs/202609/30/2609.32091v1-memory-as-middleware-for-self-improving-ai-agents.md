## 摘要
AI 智能体默认在会话之间是无状态的，因此在运行上表现出遗忘症：每个会话开始时，几乎不具备关于先前失败、修复、偏好或成功策略的持久知识。结果是，智能体会重复同样的错误，并丢弃来之不易的经验。主流的修复方式是定制记忆——将检索、持久化和学习逻辑手工接入单个智能体，并绑定到单一存储引擎。这造成了碎片化的格局：记忆无法独立于拥有它的智能体而被替换、共享、隔离或加以推理。我们认为这是一个中间件问题：智能体记忆应当成为一个一等、可插拔的层，正如数据访问、消息传递和持久化各自都成为中间件关注点一样。我们通过六个系统挑战来展开这一愿景：双向可插拔性、宿主原生介入、多租户隔离、写路径一致性、带溯源的联邦共享，以及生命周期治理。我们提出 ALTK-Evolve，一个面向自我改进智能体的记忆中间件参考实现，并用它来推动关于未来记忆中间件的更广泛研究议程。

## Abstract
AI agents are stateless across sessions by default and therefore operationally amnesic: each session begins with little durable knowledge of prior failures, repairs, preferences, or successful strategies. As a result, agents repeat the same mistakes and discard hard-won experience. The dominant fix is \emph{bespoke memory}---retrieval, persistence, and learning logic hand-wired into one agent and bound to one storage engine. This creates a fragmented landscape where memory cannot be swapped, shared, isolated, or reasoned about independently of the agent that owns it. We argue that this is a middleware problem: agent memory deserves a first-class, pluggable layer, just as data access, messaging, and persistence each became middleware concerns.   We develop this vision through six systems challenges: two-sided pluggability, host-native interposition, multi-tenant isolation, write-path consistency, federated sharing with provenance, and lifecycle governance. We present ALTK-Evolve, a reference implementation of memory middleware for self-improving agents, and use it to motivate a broader research agenda for future memory middleware.

## 1. 核心问题与整体含义（研究动机与背景）

- **根本痛点**：LLM 智能体默认跨会话无状态，导致"操作性失忆"——每个新会话几乎不携带关于先前失败、修复、偏好或成功策略的持久知识。编码助手花费一小时发现的构建标志、缺失工具或分页方案，下一会话又得从头再学。上下文窗口只是工作记忆，不是持久记忆。
- **现实后果**：随着智能体从单次聊天转向长周期软件行为体（多步规划、调用工具、多智能体协作），这种失忆从"趣闻"变成"可靠性天花板"——重复失败、部分修复、环境怪癖、部署特定约定无法被沉淀。
- **主流修复的局限**：当前做法是把记忆硬编码进单个智能体（向量库 + 检索提示 + 临时"保存有效内容"步骤）。虽有效，但记忆成为**定制（bespoke）**：与某智能体代码耦合、绑定单一存储引擎、限定单用户、对其他智能体不可见，导致每个团队重复造轮子且互不组合。
- **核心主张（Big Idea）**：智能体记忆应当成为**一等、可插拔的中间件层**，位于智能体与存储之间，向上对多种宿主（Claude Code、Codex 等）暴露统一契约，向下支持多种后端，并拥有横切关注点——隔离、一致性、共享、溯源、用户控制与生命周期治理。
- **类比依据**：数据访问、消息传递、事务、缓存、持久化都曾是被手工接入应用的逻辑，直到系统社区将其抽取为中间件。智能体记忆是下一个这样的层。
- **范围界定**：聚焦通过工具在长期运营上下文中行动的软件智能体（编码、工作流、企业智能体）；不涉及与感知和控制耦合的具身智能体。

## 2. 方法论：核心思想与关键技术细节

### 2.1 三大设计目标

- **准确性（Accuracy）**：让智能体行动更好，而非记得更多；关键是检索正确的记忆、避免陈旧/重复/矛盾记忆污染行为。
- **成本（Cost）**：以上下文 token 和执行步数计；需压缩、惰性召回、按需注入、按部署资源预算打包。
- **控制（Controls）**：按租户/范围隔离、可溯源、默认私有、可保留/审查/删除。**成本与控制是记忆成为系统问题（而非仅建模问题）的根本原因。**

### 2.2 类型化记忆模型

- 记忆分为三类，且必须存放在**独立但链接的命名空间**中：
  - **情景记忆（Episodic）**：任务/会话中发生了什么（轨迹、决策、错误、结果），体量大、按时间排序、不可变、可容忍有损摘要。
  - **语义记忆（Semantic）**：关于用户、项目、环境的稳定事实，体量小、点查、需精确、可更新。
  - **程序记忆（Procedural）**：如何执行重复性操作，按任务相似性检索、可整合。
- 若混合在单一嵌入空间，会出现**检索干扰**：一周的冗长工具调用情景会淹没几个月前一行"始终以 Java 11 为目标"的偏好——不是被遗忘，而是被数量压制。
- 统一单元为**实体（entity）**：携带内容、触发/适用条件、溯源元数据（源任务、会话、自动/手动创建）、所有权与可见性、以及（针对指南的）类别、理由、实现步骤、支持计数与成功/失败证据。

### 2.3 六大系统挑战（设计空间）

1. **双向可插拔性（Two-sided pluggability）**：下抽象异构存储（文件、pgvector、分布式向量库、托管记忆服务），上抽象异构智能体宿主；契约两侧稳定，换存储不动智能体，支持新宿主不动存储。关键缺口是缺乏类似 SQL 的**通用接口/编程模型**。
2. **宿主原生介入（Host-native interposition）**：不同宿主暴露不同介入原语（生命周期钩子、用户命令、工具协议、项目指令文件），中间件须绑定任一种并提供相同逻辑行为（行动前召回、行动后捕获），部署形态可为 sidecar、库、服务器、工具提供者或插件。
3. **多租户隔离（Multi-tenant isolation）**：命名空间是最小抽象，按用户、团队、项目、智能体、仓库、任务限定范围；隔离须贯穿存储、检索、整合、发布、删除、审计。
4. **写路径一致性（Write-path consistency）**：朴素追加式记忆会腐烂（重复、陈旧建议、过度泛化、矛盾）。写路径须是**调和问题**：决定新增、更新、合并、取代、隔离还是拒绝，而非盲目追加。调和对象不是数据项而是**行为影响**。
5. **带溯源的联邦共享（Federated sharing with provenance）**：显式可见性模型（默认私有、刻意发布）+ 联邦机制（订阅/同步而不复制整库、不抹除所有权）+ 溯源（可追溯到轨迹、用户、智能体、模型或策略）。共享同时扩大攻击面（投毒、泄露），故准入检查、溯源验证、默认私有既是治理也是安全机制。
6. **生命周期治理（Lifecycle governance）**：保留、过期、压缩、审计、批准、删除；多作者（智能体、用户、其他智能体、组织）需策略钩子界定谁能创建、批准、编辑、删除、过期、压缩、共享。

### 2.4 参考架构与实现：ALTK-Evolve

- **经验飞轮（Experience Flywheel）**：六个阶段构成闭环——**capture（捕获）→ extract（提取）→ consolidate（整合）→ store（存储）→ retrieve（检索）→ inject（注入）**，通过智能体自身闭合。
- **五接口一阶段**：捕获接口记录轨迹；提取阶段蒸馏为记忆对象；存储在后端抽象之后；检索接口选择任务相关记忆；注入路径将记忆送回智能体；提取与存储之间的整合阶段调和新旧记忆。
- **智能体面向契约**：六种逻辑操作——retrieve、write、consolidate、publish、delete、inspect。其中智能体任务中调用的是 retrieve（带类型过滤、命名空间限定、剂量感知变体：始终在线的核心高支持指南 + Top-k 任务相关）、save_trajectory、事实提取、手动实体创建、发布/取消发布、所有者校验删除。**整合与检视是控制面操作，刻意排除在智能体工具面之外**，通过客户端库、CLI 和 Web 界面暴露。
- **从轨迹到可复用记忆的四步**：
  1. **任务分段**：识别智能体实际执行的多个不同任务。
  2. **子任务识别**：分解为子任务粒度（比任务级更可复用，因许多无关任务共享认证、过滤等子任务）。
  3. **泛化**：将子任务描述与提示从任务特定实体抽象（命名播放列表 → "目标播放列表"），使记忆匹配结构相似的子任务。
  4. **聚类与整合**：按语义相似度聚类泛化子任务，合并去重簇内提示，形成比任何单例更全面的整合指南。这也使写路径一致性可行——在可复用操作层面而非逐字文本层面检测重复与矛盾。
- **目的导向的 Gisting 与分层存储**：gist 嵌入向量索引，完整原文保留在持久存储并由 gist 指针指向；gist 是索引而非替代品。压缩提示编码 gist 的用途（对话轮次突出用户属性与偏好，工具调用突出检索/计算内容、参数与结果），使被长消息稀释的简短偏好在检索中占优。工具调用 gist 与对话 gist 分命名空间存放。读取时由模型在上下文中决定：gist 不足时才从持久存储取原文（自适应记忆保真度）。
- **宿主绑定**（Table 1）：Claude Code（插件 + 项目指令文件一行导入 + skills）、Codex（全局指令文件指针）、Claw Code（携带 skills 的插件 + 可选 pre-tool-use 钩子）、IBM Bob（全局规则文件 + 命令 + MCP 服务器）。所有宿主共享同一逻辑行为——行动前召回、行动后捕获、追加式审计。

## 6. 主要结论与发现

- **记忆有效，且在最难处收益最大**（Table 3）：
  - 聚合 Task Goal：69.6% → 73.2%。
  - 更严格的聚合 Scenario Goal：50.0% → **64.3%**（+14.3 个百分点）。
  - Hard 层 Scenario Goal：19.1% → **47.6%**（翻倍以上）。
  - Easy 层 Scenario Goal：79.0% → 89.5%；Medium 层 Task Goal：66.7% → 70.8%，但 Medium 的 Scenario Goal 持平（56.2%）。
- **归因**：由于智能体模型与推理循环未变，增益可归因于作为可分离层提供的记忆，而非智能体自身变化。
- **可移植性**：同一记忆层在四个独立开发的宿主上未修改运行，验证了双向可插拔与宿主原生介入的实践可行性。
- **总体判断**：参考实现证明了设计空间的初始子集是**可实现的（realizable）**，而非仅停留在设想。
- **研究议程**：以参考实现的当前局限为起点，提出更广泛的议程——一致性模型、记忆事务与写策略、记忆准入与质量加权学习、遗忘/驱逐/压缩、部署感知打包与放置、目的导向压缩与自适应保真度、隔离与共享策略、溯源与可审计性、可移植性基准。

- **设计空间覆盖不完整**（Table 2 自述）：
  - 双向可插拔：缺少宿主/存储标准。
  - 宿主介入：缺少 sidecar 与统一标准。
  - 隔离：仅每租户+每类型命名空间，缺少层级化、基于角色的范围。
  - 写路径一致性：缺少形式化语义与事务。
  - 共享与溯源：缺少联邦策略与审计轨迹。
  - 生命周期治理：缺少保留与驱逐策略。
- **算力与可复现性信息缺失**：未披露 GPU 型号/数量、训练时长、token 消耗、成本数据；无法评估成本目标（论文自称三大目标之一）的实际达成情况。
- **应用限制**：
  - 范围明确排除具身智能体（其记忆与感知/控制耦合，约束不同）。
  - 一致性语义的等价标准是"行为等价"而非字节级，这在实践中难以验证与测试。
  - 记忆写入是多步管线（捕获→提取→整合→发布），事务语义与失败回滚尚未定义；失败的整合可能留下半合并指南可被检索，未批准候选可能影响行为。
  - 共享扩大安全与隐私攻击面（记忆投毒、个人/专有上下文泄露），当前仅有默认私有与可见性控制作为初步防线。
- **潜在偏差风险**：评估在作者自家实现上开展，虽有控制变量但缺乏第三方独立复现；AppWorld 的难度分层与结果分布（Medium 层 Scenario Goal 无提升）提示增益可能不均衡，需更细粒度分析。
