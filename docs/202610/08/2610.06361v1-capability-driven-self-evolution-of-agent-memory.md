## 摘要
记忆自演化利用任务反馈，迭代改进可执行记忆程序，这些程序存储和检索来自过去交互的信息。现有方法通常采用整体式演化，从混合反馈中推导修订方向，并通过整体性能判断进展。这可能掩盖优化方向，并隐藏因其他方面退步而被抵消的能力特定收益，导致有前景的方向未被充分探索。我们引入能力驱动的演化，将搜索指导从整体性能扩展到个体能力维度，保留有前景的修订，并将探索扩展到整体式演化的边界之外。我们提出PrisMem，它使用依赖感知的能力选择来优先考虑具有潜在跨能力收益的目标，并使用历史引导的诊断来精炼能力专家。轨迹引导的集成在成对的差异案例上比较已评估的程序，利用它们的行为差异将互补收益整合到一个统一的记忆程序中。实验表明，PrisMem在BEAM-1M和LongMemEval-M上分别比最强的基线高出10.54和7.83个百分点，证明了其在百万token历史上的有效性。

## Abstract
Memory self-evolution uses task feedback to iteratively improve executable memory programs that store and retrieve information from past interactions. Existing approaches typically adopt holistic evolution, deriving revision directions from mixed feedback and judging progress by overall performance. This can obscure optimization directions and hide capability-specific gains offset by regressions elsewhere, leaving promising directions underexplored. We introduce capability-driven evolution, which extends search guidance from overall performance to individual capability dimensions, preserving promising revisions and expanding exploration beyond the boundaries of holistic evolution. We propose PrisMem, which uses dependency-aware capability selection to prioritize targets with potential cross-capability benefits and history-guided diagnosis to refine capability specialists. Trace-guided integration compares evaluated programs on paired differential cases, using their behavioral differences to consolidate complementary gains into a unified memory program. Experiments show that PrisMem outperforms the strongest baselines by 10.54 and 7.83 percentage points on BEAM-1M and LongMemEval-M, respectively, demonstrating its effectiveness on million-token histories.

# 论文总结：Capability-Driven Self-Evolution of Agent Memory（能力驱动的智能体记忆自演化）

## 1. 核心问题与整体含义

- **背景**：记忆已成为 LLM 智能体的关键组件，需同时支持事实检索、时序追踪、偏好识别、跨会话综合等多种能力。自演化记忆将记忆表示为**可执行程序**，在训练任务上评估、由 LLM 依据任务反馈迭代修订。
- **核心问题**：现有方法普遍采用**整体式演化（holistic evolution）**——从跨能力的混合反馈中推导修订方向，仅以总体性能判断进展。这带来两个具体缺陷：
  - **优化方向模糊**：混合反馈把不同能力的失败混在一起，同一组件可能对应多种效果相反的修订（如扩大检索提升多会话推理，却引入无关个人记忆导致过度个性化）。
  - **能力收益被掩盖**：某能力的增益可能被其他能力的退步抵消。论文统计显示，**80.5% 的无整体提升的修订仍至少改进了一项能力**。
- **后果**：搜索被限制在能力空间的有限区域，整体分数提前平台化，有潜力的方向未被继续精炼。
- **核心洞见**：把演化空间从"单一整体性能维度"提升到"多能力维度"——能力级反馈提供聚焦诊断与显式方向，能力级评估保留无整体收益但有价值的修订，并可将不同方向的行为差异作为整合依据。

## 2. 方法论：PrisMem

### 2.1 核心思想
将整体式记忆演化分解为**能力专属方向**（类比棱镜分光），沿各能力维度扩展搜索边界，再把分散的收益整合回统一程序。

### 2.2 基础设定
- **问题形式化**：任务实例 $x=(H,q,y,E)$（历史、问题、参考答案、参考证据），程序 $P$ 得到得分 $s(P;x)\in[0,1]$；数据划分为 $S_{train}/S_{valid}/S_{test}$。
- **细粒度记忆接口**（5 组件）：Extraction、Indexing、Planning、Retrieval、Answer。相比常见的 "add/retrieve" 抽象，提供更局部的修改边界，便于定位失败阶段。
- **能力集合**（5 项）：Factual retrieval (F)、Temporal tracking (T)、Preference extraction (P)、Multi-session synthesis (M)、Adversarial (A)。任务由 LLM 离线标注 1 个主能力 + 最多 2 个次能力；**标签仅用于组织反馈与选择目标，绝不提供给记忆程序**，保证与基线公平对比。

### 2.3 三阶段演化流程（总预算 T=20 轮）
- **Stage I 冷启动（T1=5）**：种子程序刻意简单（按输入顺序拼接抽取单元并截断）。联合考虑全部能力反馈，快速建立平衡基座；构建**基于证据的诊断指标表**——用嵌入最大匹配相似度衡量：(i) 证据在抽取单元中的保留度 $d_{ext}$、(ii) 以证据为 oracle query 的可达性 $d_{idx}$、(iii) 对真实问题的检索效果 $d_{ret}$，据此定位 Extraction/Indexing/Planning/Retrieval 的宽泛弱点。
- **Stage II 能力精炼（T2=12）**：
  - 每个能力维护其最佳程序作为**专家（specialist）$P^\star_t(c)$**；被选中的能力从其专家出发精炼。
  - **依赖感知能力选择**：
    - 结构基率先验 $D(c_p\to c_s)$：主 $c_p$ 任务中同时需要次 $c_s$ 的比例；
    - 用专家在 $c_p$ 任务上的误差集中度 $F$ 与基率比较，超出部分 $(F-D)_+$ 乘以平均误差得到**上游误差压力** $I_t(c_p\to c_s)$；
    - 紧迫度 $U_t(c)=\bar e(c,c)+\max_{c_p\neq c} I_t(c_p\to c)$（用 max 而非 sum，避免度中心性偏置）；
    - 以历史分配次数折扣：$\rho_t(c)=U_t(c)/(1+n_t(c))$，取最大者为下一目标 $c_t$。
  - **历史引导诊断**：过滤得分 > δ=0.8 的样本，按权重 $w_t(i)$ 排序选 K=5 个案例。分子含历史表现（识别**回归见证**，便于定位近期修订影响），分母折扣被频繁选中的案例与已覆盖的次能力组合，促进诊断覆盖多样化。
  - 仅当候选在目标能力训练子集上提升、且全量评估成功时才被保留。
- **Stage III 轨迹引导整合（T3=3）**：
  - 从整体最优程序出发，规划模型按**谱系拓扑**（由近及远）确定整合顺序，编码模型执行。
  - **成对差分案例（paired differential cases）**：为每个能力选取 base 与 specialist 分差最大的训练案例，对比二者执行结果，暴露 specialist 的行为差异（收益与副作用），指导如何合并。
  - 若整合未提升整体分数，或任一能力下降超过 θ=0.1，则把失败实现与其差分案例执行结果回传给编码模型重试。

### 2.4 高效演化
- **紧凑诊断上下文**：按 2400 字符预算做贪心跨度选择（语义相似度 0.75 + 词干 Dice 重叠 0.25），保留问题/答案/证据/预测相关片段并标记省略，平均降低诊断 token **43.8%**（16,776 → 9,428）。
- **修订感知执行复用**：比较候选与其父程序，从最早受影响阶段重新执行（如仅改检索可复用已建记忆，跳过抽取与索引）。
- **程序有效性校验**：源/模块完整性 → Schema 与签名兼容性 → 功能冒烟测试 → 合成复杂度检查（约 2K 单元、100 批次、4096 维嵌入），在消耗任务模型调用前拦截可检测错误。

## 6. 主要结论与发现

- **整体性能**：
  - BEAM-1M：PrisMem 整体 **63.39%**，超过最强静态基线 11.53 pp、最强自演化基线（M⋆ 52.85%）**10.54 pp**。
  - LongMemEval-M：PrisMem 整体 **75.50%**，超过最强静态基线 8.17 pp、最强自演化基线（EvolveMem 67.67%）**7.83 pp**。
  - 几乎所有能力分项均最优，且 token 用量与其他方法相当。
- **整体式演化收益有限**：M⋆ 仅比最强静态基线高 0.99 pp（BEAM），EvolveMem 仅高 0.34 pp（LongMemEval），印证混合反馈模糊方向、聚合分数掩盖能力增益。
- **消融结论**（BEAM-1M）：
  - 去除能力驱动演化（退回整体式）**−10.15 pp** → 能力驱动是主要增益来源；
  - 去除轨迹引导整合 **−3.16 pp**（但仍优于基线）；
  - 轮询目标选择替代依赖感知选择 **−2.55 pp**；
  - 随机案例选择 **−5.26 pp** → 诊断案例与阶段目标的匹配至关重要。
- **轨迹分析**：Stage II 中能力分数**间歇性**提升，精炼一个能力也会更新其他能力的专家（反映能力间依赖）；最终整合程序接近演化过程中的能力峰值。
- **鲁棒性与可迁移性**：GPT-5.5 上仍领先基线 6.17–20.41 pp；用 Qwen3.8-27B 在 BEAM 演化的程序直接迁移到 GPT-5.5（67.25% vs 67.09%）和 LongMemEval-M（76.50% vs 75.50%）几乎无损。
- **整合优于路由**：question-only router 57.74%、oracle-label router 62.27%，均低于 PrisMem 的 63.39%；且 question-only 路由标签仅 48% 与 oracle 映射一致，说明从问题文本推断记忆需求本身很困难。

## 8. 不足与局限

- **演化与评估的规模仍偏小**：演化阶段使用 160/120（BEAM）与 60/60（LongMemEval）的训练/验证样本，20 轮预算、每轮仅 5 个诊断案例。相比搜索空间（5 组件程序的自由改写）而言，样本与轮次都相当有限，论文也观察到 Stage II 存在**间歇性提升**，暗示预算可能是限制最终性能的活跃瓶颈。
- **依赖离线能力标注**：任务需由 LLM 离线标注 1 主 + 最多 2 次能力，用于组织反馈与选择目标。虽然论文强调标签不进入程序、保证与基线公平，但**标注质量本身未被独立验证**（无人工一致性检验、无标注错误率的敏感性分析），标注偏差可能系统性地影响能力选择的优先级。
- **能力集合是固定先验**：5 项能力（F/T/P/M/A）由作者预先给定。若实际部署场景存在该集合未覆盖的需求（如工具使用记忆、多模态记忆、程序性技能记忆），机制无法自动发现新能力维度；论文未讨论能力集合的**发现/扩展机制**。
- **依赖关系建模较为粗糙**：结构基率 $D(c_p\to c_s)$ 与误差集中度 $F$ 都基于共现统计，只能捕捉**成对**依赖，无法表达三个及以上能力耦合、或条件依赖（如"仅在长历史下才需要时序+偏好联合"）。$U_t(c)$ 中取 max 是启发式选择，论文未给出该选择与其他聚合方式的对比实验。
- **超参数敏感性未系统检验**：δ=0.8（样本过滤阈值）、K=5（案例数）、θ=0.1（能力下降容忍）、T1/T2/T3=5/12/3 的划分、依赖折扣 $1+n_t(c)$ 的形式等均未做敏感性扫描，读者难以判断这些数值是稳健的还是被调优过的。
- **效率指标维度单一**：只报告 token 消耗，未给出**墙钟时间、GPU 显存、调用次数**；而修订感知执行复用、程序校验等优化主要节省的是工程开销，token 数无法完整体现其价值，也无法反映实际部署延迟。
- **评测依赖 LLM judge**：整体与能力级分数均来自 benchmark 的 LLM 评判，存在评判模型与任务模型同源（Qwen 系列）带来的**潜在自偏好**风险；论文未报告与人工评分的对齐情况。
- **统计功效有限**：部分能力子集样本极少（LongMemEval 的 Adversarial 仅 10 题），3 次运行的均值±标准差难以支撑细粒度结论；主结果的显著性检验（如配对检验）未报告。
- **成本绝对值仍高**：LongMemEval 上演化消耗 143.3M token、推理期每问题 2,232.65K token，说明该范式对**单次部署成本**要求不低，论文未讨论在预算更紧时如何退化（如减少能力维度或轮次）的可用性边界。

## 9. 对后续工作的启发

- **把"能力维度"作为通用搜索坐标系**：本文最可迁移的洞见是——只要把标量奖励拆解为可评估的多维信号，并让搜索显式感知这些维度，就能在**同一预算**下获得更高上限。该思路不限于记忆，可推广到提示优化、工具编排、多智能体角色演化等任何"反馈混合、增益被抵消"的自演化场景。
- **"无整体提升但局部有益"的修订值得保留**：80.5% 这一数字提示，任何以总分为唯一保留判据的进化框架都在**系统性丢弃中间件**；设计"专家档案 + 后期整合"的两段式结构，可能比单纯提高选择压力更有效。
- **能力依赖调度是新的研究方向**：用"结构基率 vs 实测误差集中度"的偏差识别上游瓶颈，是一个轻量且可解释的启发式。后续可探索更严谨的因果/归因方法（如反事实重放、Shapley 式能力归因）来替代共现统计。
- **整合比路由更值得投入**：表 12 的对比说明"运行时判断该用哪种记忆能力"本身就很难（question-only 路由与 oracle 标签仅 48% 一致）。这暗示未来更应研究**如何在演化期把多能力行为融合进单一程序**，而非在推理期做能力切换。
- **需要面向预算约束的调度策略**：既然 Stage II 的提升是间歇性的、且演化成本随轮次线性增长，值得研究**早停判据、收益-成本权衡、能力优先级动态重估**等机制，使方法在中小预算下仍可用。
- **能力集合的可扩展性**：一个自然的后续问题是让能力维度本身也可演化——从失败案例聚类中**自动归纳**新的能力维度，再纳入同一套调度与整合框架，从而摆脱人工先验。

## 10. 总体评价

本文的贡献重心不在单个组件的工程创新，而在于**重新定义了自演化记忆的搜索空间**：从"单一整体分数"扩展为"多能力向量 + 轨迹拓扑"。其论证链条（实证刻画失效模式 → 提出能力级分解 → 三阶段调度与整合 → 多基准、多模型、多消融验证）完整且自洽；实验在 1M-token 级别长上下文、跨模型与跨数据集迁移、以及"整合 vs 路由"的对抗性对比上做了较为克制的超额验证，公平性处理（标签不泄露、演化/测试分离、统一预算、三次运行）也较规范。主要短板集中在**超参数与标注质量的敏感性缺失、算力与时间成本披露不完整、以及依赖/能力模型的表达力有限**。整体上，这是一篇"问题定义优于技术堆叠"的工作，其能力驱动搜索的思想预计会比特定的 PrisMem 实现更具持久影响力。
